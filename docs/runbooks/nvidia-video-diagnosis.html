Browser Video Freeze — root-cause diagnosis

● Fixed & verified

Videos froze in-browser on YouTube and Hotstar — no crash, no error. This is the diagnostic path: four plausible causes eliminated by evidence, the real one found in the kernel log, and a no-sudo fix verified at the system level. CachyOS · Hyprland/Wayland · RTX 4070 Ti.

Root cause
NVIDIA open driver 610.x can't map GPU video buffers. The kernel logs nvidia_drm: Failed to map NvKmsKapiMemory; Brave's media thread dies in that path at the same instant, so the decoded frame is never presented — the picture freezes while the page keeps running.
Fix
Force the software video path via ~/.config/brave-flags.conf — sidesteps the GPU buffer that won't map. No sudo, reversible, persists across updates.
Not the cause
Pending reboot · suspend/resume · CachyOS v4 instruction mismatch · a Brave crash needing reinstall — all ruled out by evidence before the fix.

The fix

~/.config/brave-flags.conf — read by the /usr/bin/brave wrapper (it skips #/blank lines, one flag per line). No sudo; delete the file to revert.

# Force software video path — NVIDIA 610.x can't map GPU video buffers.
--disable-gpu-memory-buffer-video-frames
--disable-accelerated-video-decode
Applying it needs a full Brave restart — pkill brave (~40 procs); closing a window leaves a background process that keeps the old flags. Reopen, then check brave://version → the flags should appear in the Command Line row.

Revert & future

This is a driver-bug workaround, not a Brave defect. When a newer NVIDIA driver fixes the mapping, remove --disable-accelerated-video-decode first to get hardware (NVDEC) decode back; keep --disable-gpu-memory-buffer-video-frames if frames still stall. Other Chromium/Electron apps (Vesktop/Discord, …) using the same GPU video path may need the equivalent flag.
