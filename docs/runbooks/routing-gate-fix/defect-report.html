the hook under review

A well-intentioned gate, examined on its own code

This report critiques routing-gate.sh, the Stop hook that enforces the policy "every durable write needs non-author review". It is written for the engineer who owns the hook. The hook is well-intentioned and partly good — the tone here is engineering-honest, not dismissive; what works is credited in its own section below.

verdict

The gate is sound in posture and broken in mechanism

Its fail-open design, its report.json receipt idea, and its unusually honest limitation comments are all good. But it offers three remedies and can only observe one, it makes review-correction loops non-terminating, and its write detection is decided by which tool was used rather than what was written — so in the observed session it blocked four times over a 40-line memory note while never noticing a 70 KB user-facing deliverable.

the seven defects

Every defect, with its evidence and its fix

D1blockerThree exits offered, one implemented — options 2 and 3 are prose the hook never reads

Mechanism

The block message instructs: do ONE of (1) dispatch a batched review, (2) state the applicable named carve-out and log the review as debt, (3) state why the target was genuinely exempt.

Options 2 and 3 cannot be detected. The hook reads exactly two things:

  • the session transcript, for tool_use / tool_result pairs (lines 337-386)
  • report.json files under /tmp/{codex,opencode}-wrapper/run-*/ (lines 270-312)

There is no state file, no waiver marker, no parsing of assistant output, and no mechanism by which a stated carve-out could register. Taking option 2 is a no-op.

stop_hook_active (lines 67-68) prevents re-blocking within a single stop cycle, but each new turn is a fresh cycle.

Observed consequence

The gate fired on four separate turns for the same target. A correct, policy-sanctioned carve-out was stated twice and changed nothing, because no code path could observe it.

Net effect: option 1 is not the recommended remedy, it is the only remedy.

Proposed fix

Have the hook read a session-scoped waiver file (e.g. <session-dir>/routing-gate-waivers.jsonl) listing {path, reason, timestamp}, and treat a matching entry as coverage. This reuses the mechanism the hook already has — filesystem receipts — and converts a prose promise into an auditable record. The model can trivially write that file, but that is already true of stating a carve-out; the change strictly improves auditability rather than weakening a guarantee that does not currently exist.

D2blockerReview-correction loops cannot terminate: applying a finding is itself an uncovered write

Mechanism

The cycle is closed:

review dispatched -> findings returned -> findings applied
      -> the application is a new durable write
      -> write has a higher sequence number than the last dispatch
      -> uncovered -> gate blocks -> review dispatched -> ...

The hook has no concept of "this write is the reviewer's own proposal applied", and no per-path round cap. ~/.claude/CLAUDE.md caps review-correction loops at two rounds; the gate does not. When the two disagree the gate wins, because it is mechanical and the policy is prose.

Observed consequence

A 40-line memory note went through three review rounds. Round 3 was dispatched not because it was warranted — the correction loop was already capped and closed — but because it was the only observable way to clear the gate.

Proposed fix

Track block count per target path. After N blocks on the same path (N = 2, to match the policy cap), stop blocking and emit a non-blocking "debt logged" line instead. This makes the gate agree with the policy it is enforcing.

D3majorWrite detection depends on tool choice — cp, rm, and heredocs are invisible

Mechanism

bash_write_targets (lines 133-206) is a redirection parser. It scans for > and extracts the following word. Commands that write without redirecting are not writes as far as the gate is concerned. AMBIGUOUS_BASH (lines 129-132) additionally causes the parser to bail entirely on any command containing <<, [[, ((, $(, or a backtick.

Evidence

Verified by extracting the hook's own AMBIGUOUS_BASH, bash_write_targets and durable_path and executing them against commands from the observed session:

Command shapeDetected targets
cp "$SRC" /home/xzat/defi/misc/reviews/review-PR-572.html[] — invisible
python3 - <<'PY' … PY writing MEMORY.md[] — invisible (<< trips the bail-out)
rm -f …/memory/old.md[] — invisible (deletion is a durable change)
printf … >> /path/file['/path/file'] — detected
echo hi > /path/file['/path/file'] — detected

Observed consequence

In one session:

What was writtenHowGated?
A 40-line memory noteWrite toolBlocked 4×
The MEMORY.md index linepython heredocNever seen
A file deletion during a renamermNever seen
A 70 KB user-facing HTML deliverablecpNever seen

The hook's comments (lines 118-123) acknowledge both blind spots individually and deliberately. What is not acknowledged is the combination: Write-tool paths are gated strictly while shell-placed paths are not gated at all, so coverage is determined by tool choice rather than by what the write was or how much it mattered. The most consequential artifact of the session was never examined; the least consequential one was blocked four times.

Proposed fix

Add a fixed allowlist of writer verbs with known target-argument positions — cp, mv, install, tee, dd, rm, sed -i — roughly six entries. The hook's comment argues that detecting these "would rebuild the parser this hook removed"; a lookup table of verbs and argument positions is not a shell parser. Alternatively, if shell writes are to remain out of scope, say so in the block message so the reported count is not misread (see D6).

D4majorAny review receipt discharges any write — verified live with an unrelated session's receipt

Mechanism

review_receipt_covers (lines 270-312) accepts a receipt if:

  • report.json has mode == "review"
  • launcher_status == "ok"
  • completed_at > write_timestamp and completed_at >= session_start

It never checks what was reviewed. The report's workspace field is present in every receipt and is not consulted.

This is documented as accepted limitation #3 ("the same coarseness the existing Task/Agent path already has").

Evidence — observed live

During the session, a review receipt appeared from a different, unrelated session:

run-2AZCZgfD   workspace: /tmp/claude-1000/-home-xzat/64d125df-…/stay-awake-review-ws
               mode=review  launcher_status=ok  completed_at=2026-07-21T07:03:52Z

— reviewing an unrelated claude-stay-awake service. It landed inside the window and was fully eligible to discharge this session's gate. Nothing about the design prevents a concurrent session's work from silently satisfying another session's review requirement.

Proposed fix

Require the receipt's workspace to be a prefix of (or otherwise contain) the uncovered path. This is a small change to an existing comparison and it is the difference between a receipt meaning "a review happened somewhere" and "this write was reviewed". Note it would correctly have refused several of the observed session's own receipts, whose review workspaces were scratch copies rather than the real target directory — which is the right outcome, and would have surfaced that the scratch-workspace review pattern does not actually prove coverage of the live file.

D5majorThe only observable exit is "dispatch a worker", which rewards junk dispatches

Mechanism

Combining D1 (dispatch is the only detectable remedy) with D4 (any successful review receipt discharges every prior write) produces a clear cheapest path to clearing the gate: fire any review-mode dispatch at anything.

Observed consequence

A gate whose cheapest satisfaction is a content-free dispatch trains the behaviour it exists to prevent. This is not hypothetical — in the observed session the correct policy answer was to log debt and stop, and the gate's design pushed toward dispatching another review instead.

Proposed fix

D1 and D4 together remove the incentive: a real waiver path means the cheap exit is honest rather than performative, and workspace-scoped receipts mean a junk dispatch no longer discharges anything.

D6minorThe uncovered-target count is presented as a count of writes; it is not

Mechanism

The message reads:

1 uncovered target(s); no later dispatch to codex-wrapper / opencode-wrapper:

Given D3, this is a count of uncovered writes that happened to use a detected tool.

Observed consequence

In the observed session it reported 1 while four durable changes had occurred. A reader reasonably concludes one write happened and the rest are covered; neither is true.

Proposed fix

Either fix D3, or reword to state the scope explicitly — e.g. "1 uncovered target detected (Write/Edit tools and shell redirections only; other shell writes are not tracked)".

D7minorPolicy says memory writes need review; the practical cost is a full Codex round per note

Mechanism

durable_path (lines 88-100) excludes /dev/null, /tmp/**, and any path containing a scratchpad component. It does not exclude ~/.claude/**.

~/.claude/CLAUDE.md lists memory among durable writes requiring review, so this is arguably correct by policy. But the Superpowers section of the same file exempts "edits to ~/.claude/" from its own procedures, so the two rules pull in different directions, and the practical result is that a 40-line memory note triggers a ~7-minute heavy-model review round.

Observed consequence

Worth noting the review rounds in the observed session were not wasted — round 1 caught session-local vocabulary that would have made the note useless to a future reader, and round 2 caught that the body had been corrected while the frontmatter still carried the original over-strong claim (and the frontmatter description is what is actually loaded on recall). So the cost bought real value. The question is whether that cost should be paid automatically on every memory write or be an explicit choice.

Proposed fix

Decide deliberately: either exempt ~/.claude/** in durable_path, or leave it and accept the cost knowingly. The current state is an unexamined default rather than a decision.

credit where due

What is right about the hook

Stated because this is a defect report and would otherwise read as a condemnation:

  • Fail-open throughout. Every parse failure, missing transcript, absent python3, and malformed record path exits 0. A gate that traps a session is worse than one that occasionally misses, and the hook takes that seriously and consistently.

  • The report.json receipt is a genuinely good signal. It is the launcher's own file; a workflow cannot forge it without actually running a review. The header comments record that four earlier designs which read the notification prose all under-blocked, and abandoning prose for filesystem receipts was the correct correction.

  • The limitation comments are unusually honest — they state which direction each hole leans (over-block vs under-block), record a fix that was attempted and reverted because it regressed something worse, and explicitly warn future editors to re-run a specific sweep as a hard gate.

  • It caught a true positive. The memory writes it blocked on genuinely had no non-author review, and the reviews it forced found real problems.

The defects above are about mechanism, not intent. D1 and D2 make it unusable as specified; D3 and D4 make it unreliable as a guarantee. None of them require abandoning the design.

recommended order of work

Fix the dead ends first, then the meaning, then the scope

  1. D1 + D2 together — the waiver receipt and the per-path block cap. These are what make the gate usable; D2 without D1 just relocates the dead end. Together they would have reduced the observed session's four blocks to one.
  2. D4 — scope receipts to the write. This is what makes the gate mean something; without it, discharge can happen by coincidence, as observed.
  3. D3 + D6 — the writer-verb allowlist, or an honest scope statement in the message.
  4. D7 — a deliberate decision either way on ~/.claude/**.
