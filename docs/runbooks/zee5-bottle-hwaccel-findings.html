ZEE5 in the Wine Bottle — the Hardware-Acceleration Wall

Problem statement & debugging findings · CachyOS / Hyprland · bottle primevideo-tkg9 · 2026-06-24  BLOCKED — architectural
Verdict. ZEE5 cannot run in the Windows-Brave / Wine-TkG bottle on this machine. It demands GPU hardware acceleration, and every GPU path available to Chromium under Wine here is blocked — not by a missing flag, but by Wine's WGL/WSI limitations on this NVIDIA+Intel hybrid. Prime Video works only because it tolerates software rendering; ZEE5 does not. Fix: run ZEE5 in native Linux Brave (real hardware acceleration), keeping the same Super+Shift+Z / special:zee5 setup.

1 · Problem statement

Goal. Mirror the Prime Video setup for ZEE5: launch ZEE5 in the same Wine-TkG bottle (Windows Brave), on Super+Shift+Z with its own special:zee5 workspace.

Symptom. ZEE5's player refuses to start and shows:

Hardware Acceleration Required For Video Playback
To enable: Open Chrome Settings > System > Turn on "Use hardware acceleration when available"

The keybind, workspace routing, and window all work — ZEE5 loads, but blocks playback at the hardware-acceleration gate. The same bottle plays Prime Video at 1080p without complaint.

3 · How we got here (hypotheses ruled out)

Worked through systematically — each fix attempt, and why it failed:

  • H1 · --use-angle=gl (route the compositor via OpenGL). Window rendered, but ZEE5 still blocked. Ruled out.
  • H2 · + --ignore-gpu-blocklist (force past Chromium's GPU blocklist). No change. Ruled out.
  • Methodology fix. Realized Brave is single-instance — the running --disable-gpu process was ignoring the new flags. Re-tested by fully killing the bottle's Brave first (wineserver -k) so flags actually applied.
  • H3 · clean launch, flags genuinely applied. Still blocked. Ruled out.
  • Cleared GPU shader cache. A repeating Sharing violation on DawnGraphiteCache was noise, not the cause. Not it.
  • Evidence: brave://gpu. Definitive — every feature Software only / Disabled, with the exact failing extension named. Root cause found.

4 · Root cause — definitive, from brave://gpu

The GPU page reports Software Rendering: Yes and GL_RENDERER = SwANGLE (D3D11-WARP, a software rasterizer). Every line of the Graphics Feature Status is Software only or Disabled. The Log Messages give the precise chain:

ANGLE Display::initialize error 12289: WGL_NV_DX_interop2 is required but not present
EGL Driver message (Critical) eglInitialize: WGL_NV_DX_interop2 is required but not present
eglInitialize OpenGL failed with error EGL_NOT_INITIALIZED
Initialization of all (1) EGL display types failed
Exiting GPU process due to errors during initialization
...
media\base\win\mf_initializer.cc: Failed to start Media Foundation ... Could not load mf.dll

In plain terms: the OpenGL backend needs the WGL extension WGL_NV_DX_interop2, which Wine's WGL does not implement → GL initialization fails → the GPU process dies → Chromium falls back to a CPU rasterizer. The D3D11/Vulkan backends would use real GPU, but they hit the Vulkan swapchain (WSI) failure that blanks the window (the original Prime bug). And Media Foundation can't load (mf.dll absent — it was stripped to fix Prime's crash), so accelerated video decode is impossible regardless. There is no remaining path to hardware acceleration in this bottle.

7 · Recommendation

Run ZEE5 in native Linux Brave. It has genuine hardware acceleration, so ZEE5's gate passes and it plays. Keep the Super+Shift+Z keybind and the special:zee5 workspace — only the launcher target and the window-routing class change (native Brave is brave-browser, not the bottle's brave.exe). Prime Video is unaffected — it stays in the bottle exactly as it is.

Not pursued further (each is a deep Wine-internals project with low odds and no resolution upside over native): implementing WGL_NV_DX_interop2 in Wine, fixing the Vulkan WSI swapchain on this NVIDIA/XWayland combo, or wiring VA-API video decode through Wine.
